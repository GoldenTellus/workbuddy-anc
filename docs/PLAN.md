## 0. 读法

### 0.1 四条原则

1. **以现状为起点**——§1 是精确基线，不是"大致情况"。已完成的项不再重做。
2. **能测才算完成**——每一阶段都有 gate，gate 里每一项都能用命令验，不靠判断。
3. **不做的事默认关闭，但可翻案**——§7 列清楚，防止每次都重新讨论。
   有新信息（要求变了、形态变了）时可以翻案，**翻案要把理由写进 §7 那一行**，不是删掉了事。
4. **计划随时可变，但改要留痕**——PLAN 是「当前最佳判断」，不是合同。
   遇到下面任一情况就该当场调整，不必等走完：

   | 触发 | 例子（都真发生过） |
   |---|---|
   | **前提不成立** | 假设"技能文件有结构化标题"——实测确认了，但若不成立，L3 整个形态要改 |
   | **成本远超收益** | `database` 项的注入要停两个服务，而它只是信息项 → 砍 |
   | **出现新信息** | 厂商发版、维护者说"以后都用管理员账号"（D25）、实测推翻假设（T10 的"做不到"被 R6 推翻） |
   | **找到更简单的路** | 夜间轮换原想"切工作区"，发现传参无效、改 persona 更省 |

   **调整范围不限**：改顺序、改验收标准、拆项、合并、砍掉、加新的都行。

   **唯一不动的是 §2 的五条判据**——那是目标；其余都是手段，手段可以换。

   **但每次调整要留一行理由**（改了什么、为什么），否则半年后没人分得清这是判断还是失误。
   理由就写在对应阶段里，或本节下面。

### 0.3 阶段与命名

| 阶段 | 主题 | 一句话 |
|---|---|---|
| **S** | 稳（Stability） | 让已有的东西**不会坏**，坏了能发现 |
| **O** | 观（Observability） | 让"它到底生效了没"**能被回答** |
| **L** | 环（Loop） | 让项目**会自己变好**（上游唯一真空白） |
| **D** | 交（Delivery） | 让第二个人**能独立装起来** |

四个阶段可以部分并行，但 **S 必须在 L 之前**——一个会自己改代码的系统，不能建在会随机起不来的底座上。

另外两条依赖（不是并列关系）：

| 依赖 | 原因 |
|---|---|
| **O2 → L 的形态** | `CODEBUDDY.md` 是每轮读还是启动读，决定夜间轮换是"复制两个文件"还是"配一次重启"。不先测，L4 没法设计 |
| **S1 → R7** | 补丁启动链路不通，升级回归一跑就掉线（已在 VERIFY §16 踩过） |

**可以并行的**：O1（出站观测）与 S1 之间无依赖；L1/L2（收集与 issue）不依赖 S，可以先做。

### 2.1 闭源不构成排除理由

**WorkBuddy 是闭源产品，这不是"做不到"的理由。**

FORK D16 已裁决：允许修改、封装 WorkBuddy，允许读取它的凭据与内部数据。本项目从第一天起就跑在这条路上——**已经在用的手段**：

| 挡路的东西 | 手段 | 状态 |
|---|---|---|
| 拿不到群身份 / 发送人 | patch `preload.cjs` 包 `emitMessage`，注入 `[anc:chat=… from=…]` | **在跑**（D17） |
| 拿不到出站文本 | 包 `sendReply` | **在跑**（出站过滤挂在这） |
| 想拦自动升级检查 | 劫持 `https.request` | **在跑**（正是它导致主进程崩溃，已加进程守卫） |
| UI 操作无法自动化 | CDP / UIA | **已验证**（T6 / T13 / R6 / 出站观测都用过） |
| 深层内部行为不可见 | `app.asar` 解包 + 反编译 + `Module._compile` hook | D16 允许，按需取用 |
| 想换模型后端 | 拦模型调用层、替换端点 | **不做**（2026-11-03 裁决：单引擎部署下是负担不是能力，见 UPSTREAM-COVERAGE §3.2） |
| 进程 / 服务级别的东西 | 计划任务、服务配置、注入 inspector | 已在用（`--inspect-brk` + `inject.cjs`） |

**默认动作**：遇到"WorkBuddy 做不到"，先想"能不能**加一层**"（patch / hook / 代理 / 注入），**而不是降级需求**。

只有当"加一层"的维护成本明确高于功能价值时，才记进 §7「不做的事」，并写明代价。

> 代价要写清：每加一层，都是"随 WorkBuddy 升级而重放"的负担（`FORK §11` 台账 + R7 回归）。
> 这不是不做，是做了要维护。

### 2.4 交付形态：把 GitHub 链接发给 agent，它自己装

**这是 1.0 的交付方式，不是附加功能。**

不要：
- 不要我们去给企业部署
- 不要"发一份 300 行文档让人照做"

要：
- 企业管理员把 `https://github.com/GoldenTellus/workbuddy-anc` **发给本地电脑的 agent**
  （Claude Code / Codex / Cursor / 任何能读仓库能跑命令的）
- **agent 读完自己装**

**这意味着项目的读者变了**：

| 文档 | 现在的读者 | 1.0 要的读者 |
|---|---|---|
| `AGENTS.md` / `CLAUDE.md` | **改代码的 agent** | 保持（改代码仍然需要） |
| `REBUILD.md` | **人**（"主机坏了照这份重建"） | 改成 agent 能执行的形式，人或 agent 都能读 |
| `ONBOARDING.md` / `OPS.md` | 运维 | 保持（出事了要查） |
| **新的** | — | **部署 agent**（只拿到 URL，要自己判断环境、自己问人、自己装、自己验） |

**三个硬要求**：

1. **agent 只拿到 URL** —— 不能假设仓库已在本地，也不能假设它知道这台机器是干什么的
2. **agent 要能问人** —— 企微 corpid、部门列表、员工名单这些**不能编**，必须让它停下来问
3. **装完要能自证** —— 每一步有验证，失败要能定位到哪一步，不能"看起来装好了"

**两条路径，两套流程**：

| 路径 | 装在哪 | 谁发起 | 装完是什么状态 |
|---|---|---|---|
| **公司侧** | 一台 7×24 的主机 | 企业 IT / 管理员 | 公司 bot 在群里能回应、每天 02:00 备份、**10 个**计划任务在跑 |
| **员工侧** | 每个员工的电脑 | 员工自己（或 IT 批量） | 个人 bot 在自己群里能回应、能读写 vault、能提交问题 |

**优先让本地 WorkBuddy 自己装**（2026-11-04 补充）：

部署 agent 的第一选择**不是** Claude Code / Codex，而是**这台机器上已经/即将装好的 WorkBuddy 自己**。
理由：

- 它是唯一"装完就能干活"的东西——装完就有 persona、技能、群绑定
- 它有 `SandboxCLIClient`（能跑系统命令，`VERIFY §26` 已更正归因），所以能 clone、能读文档、能跑脚本
- 员工侧的 WorkBuddy 本来就在用，让它自己装自己是零额外成本

**但要解决鸡生蛋**：

| 侧 | WorkBuddy 装了没 | 第一步谁做 | 之后谁做 |
|---|---|---|---|
| **员工侧** | **已经装了**（员工在用） | 员工：把仓库链接贴进对话框 | **WorkBuddy 自己** |
| **公司侧** | **没装** | **人：装 WorkBuddy**（这一步它装不了自己） | **WorkBuddy 自己**（从建目录到自证） |

**所以公司侧的第一步是"装一个空 WorkBuddy"**——只要装上、能对话、能跑命令，剩下全部交给它。
这一步的说明要写进 `AGENT-DEPLOY-COMPANY.md` 的最前面，而且要写清"装完不要配任何东西，直接进下一步"。

**其它 agent 作为兜底**：如果 WorkBuddy 装不上或跑不了命令，Claude Code / Codex 也能装。
文档结构要保证两者都能执行——这其实不难，因为"能读 markdown + 能跑命令"是共同前提。

**员工侧要分部门**：

现在 `org` 数据里只有 `company` / `member` / `role` 三种，
**`role` 是岗位不是部门**（`role` 有 `duties`，是"这个岗位干什么"）。

部门要能决定：
- 这个部门的员工看到哪些 vault 目录
- 这个部门装哪些技能（不是所有部门都需要 `anc-interview`）
- 这个部门的人进哪个群

### 5.2 分层实现

| **L1** | `submission` 表 + 收集技能：识别"引用文件 @公司bot" → 落一条记录（文件 + 文本 + 谁 + 何时） | — | 群里走一次，表里有记录 |

| 生产状态 | 不许碰 `%ProgramData%\anc`（persona 禁令 + 目录 ACL 已就位） |

- **每步有明确的成功判据**，不是"应该就好了"
- **每步有回滚动作**，失败不留下半套
- **分节可跳转**，agent 只读它需要的那节（不要让 agent 一次读 300 行）
- **禁止"问我"** —— 所有要人提供的值都列成一张"开工前要问清的清单"

#### D4.2 环境自检 ✅ 2026-11-05（`VERIFY §42`）

`scripts/preflight.ps1` 检查：OS 版本 / 是否管理员 / 磁盘剩余 / 端口占用 / 已装过没有 / D 盘存不存在 / PowerShell 版本。

**输出要能让 agent 直接判断**：`{ok, blockers[], warnings[], next}`。

**为什么必须**：agent 不知道这台机器是什么状态。有 preflight，它才能决定"继续装 / 停下来问 / 先修某个前置"。

#### D4.3 分阶段 + 断点续装 ✅ 2026-11-05（`VERIFY §43`）

- 每个阶段有独立状态文件（`%ProgramData%\anc\data\deploy-state.json`）
- 记录：`{stage, done[], failed, at}`
- **agent 重跑时从 failed 那步接着做**，不从头再来

**为什么必须**：装到"打补丁"失败（这台机器上补丁链折腾过很多次），不能要求从头来一遍。

#### D4.4 部门结构 ✅ 2026-11-05（`VERIFY §44`）

`org` 数据加 `dept`。文件 `org/depts/<id>.md`：

```yaml
---
id: engineering
name: 研发部
vault_paths: [shared/工艺, internal/研发]
skills: [anc-task, anc-vault-read, anc-feedback]
---
```

`member` 加 `dept: engineering`。

**部门决定三件事**：
1. 员工看到哪些 vault 目录
2. 装哪些技能（不是每个部门都要 `anc-interview`）
3. 进哪个群（将来"一部门一群"时的依据）

**渲染器要跟着改**：`KNOWN_KEYS` 加 `dept`，成员引用不存在的部门要报错（和 `role` 一样的处理）。

#### D4.5 自证 ✅ 2026-11-05（`VERIFY §45`；SKIP 分支未实测）

装完不是"我说装好了"，是：

| 侧 | 自证方式 |
|---|---|
| 公司侧 | `doctor` FAIL=0 + 往群里发一条消息能被 bot 回应 + `cli task add` 能落库 |
| 员工侧 | 个人 bot 上线 + 能被 @ 回应 + 能读 vault 里一个文件 |

**agent 要能把结果说清**：

```
公司侧部署：完成
  doctor: FAIL=0 WARN=1（vault-ingest-audit 基线）
  群回应: OK（"在。"）
  任务落库: OK（task #1）
  9 个计划任务: 全部 Ready
未完成: 无
```

#### D4.6 验收（这条判据怎么算过）⬜ **要真机 + 陌生 agent，本机做不了**

**在一台没装过本项目的机器上，装一个空 WorkBuddy，然后把下面这句贴给它**：

```
https://github.com/GoldenTellus/workbuddy-anc
照这个仓库把自己装成公司侧。装完告诉我装到哪一步、哪一步卡住了、怎么解决的。
```

**它装完并且不用问本仓库作者 = 判据过。**

**兜底验收**：如果 WorkBuddy 那台机器装不上，换 Claude Code / Codex 重跑同一个问题。
两者都过 = 文档真的可执行；只有一个过 = 文档耦合了某个 agent 的特定能力，要改。

**失败也要记**：卡在哪一节、文档缺什么、它猜错了什么。**那才是这份文档的真实质量。**

## 7. 不做的事（默认关闭，可翻案）

| 不做 | 理由 | 什么情况下翻案 |
|---|---|---|
| **无人 review 的自动合入**（devbot 自己做，但合入 main 要人看） | 上游也是 review 在 merge 前；这是分工不是降级 | 出现"能证明改对了"的机制（eval 能测模型遵从度），且分支级隔离被验证过 |
| **员工电脑当 devbot** | 员工电脑不 7×24；要装 git / 连仓库；额度归属不清 | 主机算力不够、issue 队列排不过来；且员工电脑有 git + 能连仓库；且额度归属说清 |
| **第二个 WorkBuddy 实例** | 已验证不可行（单实例锁，退出码 9） | WorkBuddy 放开多实例（现在单实例锁挡住，退出码 9） |
| **多公司单机** | 一机一公司（上游 v1 也不支持） | 上游支持了，或要服务第二家公司时重新评估 |
| **自建 IM 网关 / 自建 agent 框架** | 项目边界（用 WorkBuddy + 企微） | WorkBuddy 不再提供企微通道，或补丁路径彻底走不通 |
| **把 vault 迁到云端** | D14/D19 | D19 被推翻（资料不上云不再要求） |
| ~~**`database` 项的 doctor 注入**~~ | **2026-11-04 已做，原判断是错的**：不用停服务——用 `-Root` 指向演练根就能注（`VERIFY §39`），而且它有完整 FAIL 分支（不是"信息项"）。顺带修了该项忽略 `-Root` 的硬编码 | 找到不停服务的注入方式（如改文件内容而非挪走） |

## 8. 时间与分工（2026-11-05 重写）

**原估时（2026-11-03 版）已作废**：S / O / L 三天跑完，D 卡在外部环境。

现在不看「开发工作量」，看「四阶段各要多久、谁做」：

| 阶段 | 谁 | 估时 | 卡不卡 |
|---|---|---|---|
| **A 补代码缺口** | agent | 半天 | 不卡，随时能开始 |
| **B 证明代码能自愈** | agent | 1 小时 | 不卡 |
| **C 清空重装** | 维护者 + agent | 4–6 小时（装 / 升级 / 查红 / 修） | **卡维护者在场** |
| **D 陌生 agent 装** | 维护者开会话 + agent 跑 | 1–2 小时 | **卡维护者开会话** |

**关键路径**：`A → B → C → D`，**不能跳**。

**为什么不能先 C**：现在 `doctor` 全绿依赖 5 处手工 `icacls`（`VERIFY §65`）。
先清空的话，重装完一片红，分不清是「脚本有 bug」还是「本来就缺这块」——
那等于把一次干净的清空浪费掉。

**所以 1.0 的「完成时间」现在取决于维护者什么时候有空做 C 阶段那 9 件事**，不取决于开发。

## 9. 风险登记（本计划新增）

| 风险 | 等级 | 应对 |
|---|---|---|
| 补丁机制随 WorkBuddy 升级失效，且无法自动恢复 | **高** | S1 把"确定性"做出来；R7 是 gate |
| 迭代闭环的 patch draft 产不出可用的 diff | **中** | L3 先做、先证伪，不行就停在"人工改 + 自动诊断" |
| eval 依赖驱动 UI，WorkBuddy 一升级就坏 | **中** | 承认这个代价；eval 失败只标记不阻断 |
| devbot 改坏技能且人工没看出来 | **中** | review 闸不能省；分支级隔离；快速回滚（1 分钟） |
| **devbot 不会自己启动**：`allOff` 没人消费，夜间跑的是固定时间任务 | **中** | 补一个调度器（22:00 起每 30 分钟查一次 `all-off`）；**难点是规则不是代码**——空名册（周末/请假）时 `allOff=false`，得先定"什么算可以开跑" |
| **devbot 只改 4–8 行**：它能改的是"SKILL.md 里某一段的措辞"，改不了代码逻辑 | 低 | 承认边界；大改仍然要人写 |
| **`run_command` 能跑任意系统命令**：这是整条链的根基，persona 里四条"不许"是约束不是沙箱 | **中** | 分支级隔离 + 事后五项检查（`§27`）；生产状态有 ACL |
| **模型行为不稳定**：`§27` 记了同一类 issue 两次写不同字段；`task-list-one-line` 自己变绿过 | **中** | **验收钉在副作用上（库变没变、日志有没有新行），不钉在措辞上**（`§36` 记了这个教训） |
| 观测落盘带来隐私问题 | 低 | 只记数字不记内容（O1 的设计） |
| **历史 commit 带真实 chatId**（35 个） | **中** | 仓库 private；转 public 前必须 `git filter-repo`。HEAD 已干净，`check-public` 已补三类模式 |

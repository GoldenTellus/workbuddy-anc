## 0. 读法

### 0.1 四条原则

1. **以现状为起点**——§1 是精确基线，不是"大致情况"。已完成的项不再重做。
2. **能测才算完成**——每一阶段都有 gate，gate 里每一项都能用命令验，不靠判断。
3. **不做的事默认关闭，但可翻案**——§8 列清楚，防止每次都重新讨论。
   有新信息（要求变了、形态变了）时可以翻案，**翻案要把理由写进 §8 那一行**，不是删掉了事。
4. **计划随时可变，但改要留痕**——PLAN 是「当前最佳判断」，不是合同。
   遇到下面任一情况就该当场调整，不必等走完：

   | 触发 | 例子（都真发生过） |
   |---|---|
   | **前提不成立** | 假设"技能文件有结构化标题"——实测确认了，但若不成立，L3 整个形态要改 |
   | **成本远超收益** | `database` 项的注入要停两个服务，而它只是信息项 → 砍 |
   | **出现新信息** | 厂商发版、维护者说"以后都用管理员账号"（D25）、实测推翻假设（T10 的"做不到"被 R6 推翻） |
   | **找到更简单的路** | 夜间轮换原想"切工作区"，发现传参无效、改 persona 更省 |

   **调整范围不限**：改顺序、改验收标准、拆项、合并、砍掉、加新的都行。

   **唯一不动的是 §2 的五条判据**——那是目标；其余都是手段，手段可以换。

   **但每次调整要留一行理由**（改了什么、为什么），否则半年后没人分得清这是判断还是失误。
   理由就写在对应阶段里，或本节下面。

### 0.3 阶段与命名

| 阶段 | 主题 | 一句话 |
|---|---|---|
| **S** | 稳（Stability） | 让已有的东西**不会坏**，坏了能发现 |
| **O** | 观（Observability） | 让"它到底生效了没"**能被回答** |
| **L** | 环（Loop） | 让项目**会自己变好**（上游唯一真空白） |
| **D** | 交（Delivery） | 让第二个人**能独立装起来** |

四个阶段可以部分并行，但 **S 必须在 L 之前**——一个会自己改代码的系统，不能建在会随机起不来的底座上。

另外两条依赖（不是并列关系）：

| 依赖 | 原因 |
|---|---|
| **O2 → L 的形态** | `CODEBUDDY.md` 是每轮读还是启动读，决定夜间轮换是"复制两个文件"还是"配一次重启"。不先测，L4 没法设计 |
| **S1 → R7** | 补丁启动链路不通，升级回归一跑就掉线（已在 VERIFY §16 踩过） |

**可以并行的**：O1（出站观测）与 S1 之间无依赖；L1/L2（收集与 issue）不依赖 S，可以先做。

## 2. 1.0 的定义

**1.0 = 能交给第二个人用，并且它会自己变好。**

四条判据，全部可测：

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | **40 条 DoD 全绿** | `ACCEPTANCE.md` 无 🟡 |
| 2 | **补丁在升级后能自愈** | 走一次 R7（真升级回归），补丁在 1 分钟内恢复，bot 不掉 |
| 3 | **迭代闭环跑通一次** | 从"员工提交一个问题"到"合入一个改好的技能"，全程有记录 |
| 4 | **第二个人能独立装** | 按 `REBUILD.md` 从零装完，不出自本仓库作者的隐性知识 |
| 5 | **覆盖上游全部功能模块，零差距** | `UPSTREAM-COVERAGE.md` 的 20 个模块**逐项有结论**：✅ 等价实现 / 🔄 **换机制达成**（REUSE-MAP §3.1 口径，不算缺口）/ 已论证的 ➖ 不适用；**不留 ⬜（真空白）和 🟡（未论证的语义差异）**  **2026-11-04 达成**：`✅13 / 🔄6 / ➖2 / 🟡0 / ⬜0`，逐项论证见 `VERIFY §30` |

### 2.1 闭源不构成排除理由

**WorkBuddy 是闭源产品，这不是"做不到"的理由。**

FORK D16 已裁决：允许修改、封装 WorkBuddy，允许读取它的凭据与内部数据。本项目从第一天起就跑在这条路上——**已经在用的手段**：

| 挡路的东西 | 手段 | 状态 |
|---|---|---|
| 拿不到群身份 / 发送人 | patch `preload.cjs` 包 `emitMessage`，注入 `[anc:chat=… from=…]` | **在跑**（D17） |
| 拿不到出站文本 | 包 `sendReply` | **在跑**（出站过滤挂在这） |
| 想拦自动升级检查 | 劫持 `https.request` | **在跑**（正是它导致主进程崩溃，已加进程守卫） |
| UI 操作无法自动化 | CDP / UIA | **已验证**（T6 / T13 / R6 / 出站观测都用过） |
| 深层内部行为不可见 | `app.asar` 解包 + 反编译 + `Module._compile` hook | D16 允许，按需取用 |
| 想换模型后端 | 拦模型调用层、替换端点 | **不做**（2026-11-03 裁决：单引擎部署下是负担不是能力，见 UPSTREAM-COVERAGE §3.2） |
| 进程 / 服务级别的东西 | 计划任务、服务配置、注入 inspector | 已在用（`--inspect-brk` + `inject.cjs`） |

**默认动作**：遇到"WorkBuddy 做不到"，先想"能不能**加一层**"（patch / hook / 代理 / 注入），**而不是降级需求**。

只有当"加一层"的维护成本明确高于功能价值时，才记进 §8「不做的事」，并写明代价。

> 代价要写清：每加一层，都是"随 WorkBuddy 升级而重放"的负担（`FORK §11` 台账 + R7 回归）。
> 这不是不做，是做了要维护。

### 2.2 能用上游的就用

**默认复用，不重复造。** 顺序写死：

1. 先查 `docs/REUSE-MAP.md`——上游这块有没有现成设计/代码
2. 再查 `reference/upstream/`——有没有已导入的参考件
3. 最后才自己写；自己写时，**结构照上游的概念**，不另发明一套

| 上游有什么 | 本项目的处理 |
|---|---|
| 完整实现（如渲染器） | **搬**（来自 `feat-m1-w1`） |
| 骨架可用（如 vault-service 的 MCP RPC） | **备着**，需要时改 |
| 只有设计（如迭代闭环、七段式 persona） | **按概念实现**，不简化 |
| 前提不成立（如 cc-connect、Cloudflare 部署） | 换机制达成**同一目的**，并在 `UPSTREAM-COVERAGE.md` 写明差异 |

### 2.3 零差距的逐项判定

`UPSTREAM-COVERAGE.md` 里 20 个模块，"零差距"按**功能等价**判，不要求实现相同：

| 上游模块 | 现状 | 到零差距要做什么 |
|---|---|---|
| Gateway（cc-connect） | ✅ 功能等价 | 本项目用 WorkBuddy 内置企微通道，"接入 IM"这个功能已覆盖 |

## 5. 阶段 L：环（让项目会自己变好）

> 这是**上游唯一真空白**（UPSTREAM-COVERAGE §3.1）。
> gate L 的判据：**从"员工提交一个问题"到"合入一个改好的技能"，全程有记录、能复现。**

### 5.1 设计（已定，来自本轮对话）

```
【收集】员工侧零学习成本
  @个人bot 说「下班」        → cli dayend（纯记录，不调模型）
  发文件到三人群
  引用文件 @公司bot + 说问题  → 公司bot 落一条 submission

【汇总】主机，自动
  submission → 结构化 issue {skill, section, symptom, expected, verify}

【devbot】主机，夜间
  读 issue → 改仓库 → 出分支 → 不 deploy

【eval】主机，自动
  驱动 WorkBuddy 回放关键用例 → 不过就标记该分支有问题

【合入】人，早上 5 分钟
  git diff → 合入 → deploy.ps1
```

**关键设计决策**（本轮已定，不重开）：

| 决策 | 结论 | 理由 |
|---|---|---|
| devbot 跑在哪 | **主机**，同实例夜间轮换 | 同机第二实例已验证不可行（单实例锁） |
| 轮换机制 | 改 `CODEBUDDY.md`（待 O2 确认读盘时机） | 传参切工作区已验证无效 |
| 员工的 WorkBuddy 参与吗 | **不参与**，只负责"说一句 + 发文件" | 员工电脑不 7×24，且要装 git / 连仓库 |
| eval 测什么 | 驱动 WorkBuddy 回放，比对回答 | CDP 能力已有（T6/T13/R6 用过） |

### 5.2 分层实现

| 子项 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| **L1** | `submission` 表 + 收集技能：识别"引用文件 @公司bot" → 落一条记录（文件 + 文本 + 谁 + 何时） | — | 群里走一次，表里有记录 |
| **L2** | `cli issue draft`：submission → 结构化 issue（规则表：关键词 → 技能 → 段落） | L1 | 一条 submission 出一个 issue |
| **L3** | `cli patch draft`（**模板版**）：issue → 定位段落 → 插入 `patch_hint` → 输出 diff | L2。**前提已验证**：技能文件有清楚的 `## 标题`（如 `## 查任务`、`## 登记任务`、`## 完成 / 取消`），能按 section 定位 | 用 3 条假 issue 验证 diff 可读 |
| **L4** | **devbot 全自动**：夜间切 persona → 读 issue 队列 → 改 → 出分支（对齐上游：从问题到补丁无人介入） | **O2 结论** + S1 | 一次夜间跑出 1 个可用分支 |
| **L5** | `cli dayend` + 全员下班判定（"所有人都下班" → 开夜间窗口） | L1 | 群里说"下班"，表里有记录 |
| **L6** | eval runner：驱动 WorkBuddy 回放一条用例，比对回答 | L4 | 一条用例能跑出 pass/fail |
| **L7** | 端到端：一条真实反馈 → 合入一个技能改动 | 全部 | 走通一次，全程留痕 |

**顺序理由**：L3 的模板版先做——**如果它产不出你愿意合入的 diff，L4 的 agent 版就是"把不可用的产出复制 N 份"**。L3 是整条链的风险点，值得先证伪。

### 5.3 隔离（devbot 能改仓库，不能碰生产）

三层，都不需要新建：

| 层 | 手段 |
|---|---|
| 代码 | devbot 只提交到 `devbot/issue-<N>` 分支，不碰 main |
| 部署 | persona 里写死"不许跑 deploy.ps1"；即便跑了，`deploy` 也是幂等的 |
| 生产状态 | 不许碰 `%ProgramData%\anc`（persona 禁令 + 目录 ACL 已就位） |

**最坏后果**：产出一个烂分支，`git branch -D` 就没了。

## 8. 不做的事（默认关闭，可翻案）

| 不做 | 理由 | 什么情况下翻案 |
|---|---|---|
| **无人 review 的自动合入**（devbot 自己做，但合入 main 要人看） | 上游也是 review 在 merge 前；这是分工不是降级 | 出现"能证明改对了"的机制（eval 能测模型遵从度），且分支级隔离被验证过 |
| **员工电脑当 devbot** | 员工电脑不 7×24；要装 git / 连仓库；额度归属不清 | 主机算力不够、issue 队列排不过来；且员工电脑有 git + 能连仓库；且额度归属说清 |
| **第二个 WorkBuddy 实例** | 已验证不可行（单实例锁，退出码 9） | WorkBuddy 放开多实例（现在单实例锁挡住，退出码 9） |
| **多公司单机** | 一机一公司（上游 v1 也不支持） | 上游支持了，或要服务第二家公司时重新评估 |
| **自建 IM 网关 / 自建 agent 框架** | 项目边界（用 WorkBuddy + 企微） | WorkBuddy 不再提供企微通道，或补丁路径彻底走不通 |
| **把 vault 迁到云端** | D14/D19 | D19 被推翻（资料不上云不再要求） |
| **`database` 项的 doctor 注入** | 要停两个服务 + 杀进程，而它只是**信息项**（报文件大小，不参与判断）。27/28 项已覆盖判断类检查，风险 > 收益 | 找到不停服务的注入方式（如改文件内容而非挪走） |
| **专门造一个逾期任务去验改法 A** | 改法已部署、fixture 里验过；真实逾期任务**等一天自然会有**，不值得专门造 | 长期没有自然出现的逾期任务，且怀疑改法有 bug |
| **日报**（token 用量 / 活跃度 / 问题挖掘） | 单人单机，`doctor` 的 28 项探针已经答了"坏没坏"；日报没人读。**不是做不到，是不值得** | 员工数到 10 人以上、或开始按 bot 分摊成本 |
| **`anc-interview` 技能长期常驻** | 访谈是**一次性调研**。R4 做完后，问题清单归档到 vault 即可，技能本身退役（不是"不做访谈"，是"不让它一直挂着"） | 有第二家公司要试点（访谈要重做） |
| **把 tool-turn-filter 升级成结构判断** | 词表判据弱，但**成本低、不误伤功能**。为它去逆向工具轮次结构，收益不抵（出站过滤保持词表） | 出站噪声真的影响到使用时（现在只是"不够干净"） |

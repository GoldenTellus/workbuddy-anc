>

## 0. 读法

### 0.1 三条原则

1. **以现状为起点**——§1 是精确基线，不是"大致情况"。已完成的项不再重做。
2. **能测才算完成**——每一阶段都有 gate，gate 里每一项都能用命令验，不靠判断。
3. **不做的事写死**——§6 列清楚，防止范围蔓延。

### 0.2 与其它文档的关系

| 文档 | 关系 |
|---|---|
| `FORK-DIRECTION.md` | 设计裁决的唯一真相源（D1–D25）。本计划不新立裁决，需要裁决时标 `[待裁决]` |
| `ACCEPTANCE.md` | 40 条终态 DoD 的逐条证据表。本计划的 gate 直接引用它 |
| `VERIFY.md` | 实测记录（§1–§16）。§16 是本计划阶段 S 的起因 |
| `UPSTREAM-COVERAGE.md` | 上游 20 个模块的覆盖对照，指出唯一真空白是"迭代闭环"（本计划阶段 L） |

### 0.3 阶段与命名

| 阶段 | 主题 | 一句话 |
|---|---|---|
| **S** | 稳（Stability） | 让已有的东西**不会坏**，坏了能发现 |
| **O** | 观（Observability） | 让"它到底生效了没"**能被回答** |
| **L** | 环（Loop） | 让项目**会自己变好**（上游唯一真空白） |
| **D** | 交（Delivery） | 让第二个人**能独立装起来** |

四个阶段可以部分并行，但 **S 必须在 L 之前**——一个会自己改代码的系统，不能建在会随机起不来的底座上。

## 3. 阶段 S：稳（让已有的东西不会坏）

> gate S 的判据：**把主机彻底重启一次，bot 在 3 分钟内恢复到"补丁已加载 + 群里能应答"。**

### S1 补丁启动链路加固 ★核心

**问题**（VERIFY §16）：`--inspect-brk` + inject 设 `NODE_OPTIONS` 这条路在彻底重启后走不通。现在靠 `patch-guard` 每分钟兜底，但这是"补救"不是"设计"。

要做三件事：

| 子项 | 内容 | 验收 |
|---|---|---|
| S1.1 | 摸清 `patch-guard` 到底怎么补齐注入的（它跑什么、注入到哪个进程） | 写清在 `docs/WORKBUDDY-PATCH.md` |
| S1.2 | 把"开机即就位"做成确定路径：WorkBuddy 启动后 60 秒内必须 `APPLIED`，不依赖运气 | 冷启动 3 次，3 次都成 |
| S1.3 | 失败告警：60 秒没 `APPLIED` 就发群消息（`alertOps` 已有） | 人为让注入失败，看告警到不到 |

**为什么这条必须在 L 之前**：一个会自己改技能的系统，如果底座会随机起不来，改出来的东西根本没法验证。

### S2 升级回归 R7（事件触发，但必须准备就绪）

- 厂商发新版 → WorkBuddy 升级 → 补丁重放 → 群消息验证
- **S1 做完才能做这条**，否则升级后大概率掉线
- 触发条件：WorkBuddy 出现新版本号（`anc-update-watch` 已经在看）

### S3 逾期任务改法 A 的真实验证

改法 A（逾期任务当天继续提醒）已实现并部署，但只在 fixture 上验过。

| 子项 | 做法 |
|---|---|
| S3.1 | 造一个真实的逾期任务（昨天到点没完成），看今天是否正常催 |

### gate S


## 4. 阶段 O：观（让"生效了没"能被回答）

> gate O 的判据：**对"出站过滤到底有没有生效"这个问题，能给出带证据的答案。**

### O1 出站过滤：先能看见

**问题**：过滤代码在、部署了、`patch` 项 PASS，但**没有任何痕迹证明它被调用过**。而 19:13 那次回复带明显旁白。

**三个未知，改法完全不同**：

| 未知 | 如果是它 | 改法 |
|---|---|---|
| 群消息走 `sendStreamChunk` 不走 `sendReply` | 过滤没跑到 | 换挂载点 |
| 每次只发一行（单行规则跳过） | 过滤跑了但放行 | 改单行规则 |
| 词表没匹配上 | 过滤正常、判据弱 | 补词表 |

**做法**：观测落盘（已写代码，未上线，`759b19d`）

```
sendReply 调用时：原文行数 / 过滤后行数 / 丢了几行
sendStreamChunk：只计数（判是否流式才是主出口）
→ %USERPROFILE%\anc\narration-filter.log
```

**只记数字不记内容**——原文可能有业务正文，落盘等于搬到另一个地方。

| 子项 | 验收 |
|---|---|
| O1.1 | 观测上线，触发一次入库 + 一次普通问答，日志有数据 |
| O1.2 | 按日志判定三种情况里的哪一种，写进 VERIFY |
| O1.3 | 按判定结果决定改不改（**不预设要改**） |

### O2 夜间轮换验证（决定阶段 L 的形态）

**问题**：`CODEBUDDY.md` 是**每轮读**还是**启动读**？

| 结论 | 对 L 的影响 |
|---|---|
| 每轮读 | 夜间轮换 = 复制两个文件，**最省事** |
| 启动/新会话读 | 轮换要配一次重启（依赖 S1 的加固） |

**做法**：往 `CODEBUDDY.md` 加一句独特标记 → 群里问一句 → 看是否体现。**5 分钟，不重启，随时可回滚。**

（已验证**不可行**的两条：传目录参数切工作区 —— 退出码 1、projects 时间戳没变；同机第二实例 —— 退出码 9，单实例锁。）

`database`（需停两个服务 + 杀进程，留维护窗口）、`vault-ingest-audit`（基线即 WARN，已有真实触发观察）。

| 子项 | 验收 |
|---|---|
| O3.1 | `database` 在维护窗口里注入一次，确认会 FAIL 且能恢复 |

### gate O

## 5. 阶段 L：环（让项目会自己变好）

> 这是**上游唯一真空白**（UPSTREAM-COVERAGE §3.1）。
> gate L 的判据：**从"员工提交一个问题"到"合入一个改好的技能"，全程有记录、能复现。**

### 5.1 设计（已定，来自本轮对话）

```
【收集】员工侧零学习成本
  @个人bot 说「下班」        → cli dayend（纯记录，不调模型）
  发文件到三人群
  引用文件 @公司bot + 说问题  → 公司bot 落一条 submission

【汇总】主机，自动
  submission → 结构化 issue {skill, section, symptom, expected, verify}

【devbot】主机，夜间
  读 issue → 改仓库 → 出分支 → 不 deploy

【eval】主机，自动
  驱动 WorkBuddy 回放关键用例 → 不过就标记该分支有问题

【合入】人，早上 5 分钟
  git diff → 合入 → deploy.ps1
```

**关键设计决策**（本轮已定，不重开）：

| 决策 | 结论 | 理由 |
|---|---|---|
| devbot 跑在哪 | **主机**，同实例夜间轮换 | 同机第二实例已验证不可行（单实例锁） |
| 轮换机制 | 改 `CODEBUDDY.md`（待 O2 确认读盘时机） | 传参切工作区已验证无效 |
| 员工的 WorkBuddy 参与吗 | **不参与**，只负责"说一句 + 发文件" | 员工电脑不 7×24，且要装 git / 连仓库 |
| eval 测什么 | 驱动 WorkBuddy 回放，比对回答 | CDP 能力已有（T6/T13/R6 用过） |

### 5.2 分层实现

| 子项 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| **L1** | `submission` 表 + 收集技能：识别"引用文件 @公司bot" → 落一条记录（文件 + 文本 + 谁 + 何时） | — | 群里走一次，表里有记录 |
| **L2** | `cli issue draft`：submission → 结构化 issue（规则表：关键词 → 技能 → 段落） | L1 | 一条 submission 出一个 issue |
| **L3** | `cli patch draft`（**模板版**）：issue → 定位段落 → 插入 `patch_hint` → 输出 diff | L2 | 用 3 条假 issue 验证 diff 可读 |
| **L4** | devbot 接线：夜间切 persona → 读 issue 队列 → 改 → 出分支 | **O2 结论** + S1 | 一次夜间跑出 1 个可用分支 |
| **L5** | `cli dayend` + 全员下班判定（"所有人都下班" → 开夜间窗口） | L1 | 群里说"下班"，表里有记录 |
| **L6** | eval runner：驱动 WorkBuddy 回放一条用例，比对回答 | L4 | 一条用例能跑出 pass/fail |
| **L7** | 端到端：一条真实反馈 → 合入一个技能改动 | 全部 | 走通一次，全程留痕 |

**顺序理由**：L3 的模板版先做——**如果它产不出你愿意合入的 diff，L4 的 agent 版就是"把不可用的产出复制 N 份"**。L3 是整条链的风险点，值得先证伪。

### 5.3 隔离（devbot 能改仓库，不能碰生产）

三层，都不需要新建：

| 层 | 手段 |
|---|---|
| 代码 | devbot 只提交到 `devbot/issue-<N>` 分支，不碰 main |
| 部署 | persona 里写死"不许跑 deploy.ps1"；即便跑了，`deploy` 也是幂等的 |
| 生产状态 | 不许碰 `%ProgramData%\anc`（persona 禁令 + 目录 ACL 已就位） |

**最坏后果**：产出一个烂分支，`git branch -D` 就没了。

### gate L

```
□ 群里"引用文件 @公司bot"能落 submission
□ submission 能转成结构化 issue
□ patch draft 的 diff 你愿意合入（至少一条）
□ 夜间跑出一批分支
□ eval 能判定 pass/fail
□ 端到端走通一次，全程有记录
```

## 8. 不做的事（写死）

| 不做 | 理由 |
|---|---|
| **全自动 devbot（无人 review 直接合入）** | 缺 eval 兜底（只能测确定性部分，测不了模型遵从度）；弱信号驱动强改动，风险不对等 |
| **员工电脑当 devbot** | 员工电脑不 7×24；要装 git / 连仓库；额度归属不清 |
| **第二个 WorkBuddy 实例** | 已验证不可行（单实例锁，退出码 9） |
| **多公司单机** | 一机一公司（上游 v1 也不支持） |
| **自建 IM 网关 / 自建 agent 框架** | 项目边界（用 WorkBuddy + 企微） |
| **把 vault 迁到云端** | D14/D19 |

## 10. 风险登记（本计划新增）

| 风险 | 等级 | 应对 |
|---|---|---|
| 补丁机制随 WorkBuddy 升级失效，且无法自动恢复 | **高** | S1 把"确定性"做出来；R7 是 gate |
| 迭代闭环的 patch draft 产不出可用的 diff | **中** | L3 先做、先证伪，不行就停在"人工改 + 自动诊断" |
| eval 依赖驱动 UI，WorkBuddy 一升级就坏 | **中** | 承认这个代价；eval 失败只标记不阻断 |
| devbot 改坏技能且人工没看出来 | **中** | review 闸不能省；分支级隔离；快速回滚（1 分钟） |
| 观测落盘带来隐私问题 | 低 | 只记数字不记内容（O1 的设计） |

# anc-onboard:一场访谈,建出你公司的共享 vault

> 基于上游 `light/skills/anc-onboard` 改写:vault 从云端服务改为主机本地目录,写入从 MCP 工具改为直接写文件 + git 提交。

## 铁律(置顶)

- 访谈产出的一切内容必须来自用户的回答,**绝不替用户编造业务事实**;没问到的写 `TBC`。
- **只在主机的 WorkBuddy 桌面端、由管理员运行。** 如果是在企业微信里被触发,停止并回复「建库只能由管理员在主机上进行」。
- 建库前必须确认能读写 vault 根目录(见步骤 0);做不到就停下来说明原因,不要假装写入成功。
- 只读写 vault 根目录之内的文件(vault 根目录见工作区指令,默认 `C:\anc\vault\`)。唯一允许运行的命令是在 vault 根目录执行 `git add`、`git commit`、`git status`。

## 对话即界面:进度汇报约定(每轮必守)

没有前端,对话就是全部界面。onboarding 的**每一轮回复**都必须让管理员一眼看清三件事:

1. **回复第一行永远是进度行**,格式:`【onboarding 3/5 · 资料写入】已建 5 个文件,正在写 roles/ ——接下来还差成员名单`。五个阶段:① 确认 vault ② 访谈 ③ 目录设计确认 ④ 写入 ⑤ 收尾交付。
2. 每轮结尾明确说**下一步需要用户给什么**(一句话,别让人猜)。
3. **断点续走靠 vault 自己**:每完成一个阶段,立即写 `company/onboarding-state.md`,记录阶段勾选清单与已收集的关键信息摘要,并提交一次(`git commit -m "onboarding: 阶段 n 完成"`)。skill 每次启动第一件事(确认 vault 后)就是读这个文件:存在且未完成 → 播报「上次进行到第 n 步」并从中断处继续,已完成 → 转日常使用指引。中途关掉会话也不丢进度。

## 前置:主机已搭好

按仓库 `workbuddy/HOST-SETUP.md` 完成第 1-6 步:vault 目录已建好并 `git init`,公司 bot 的 WorkBuddy 已登录,本技能已安装。

## 步骤

### 0. 确认 vault

列出 vault 根目录的内容,并运行 `git status` 确认它是 git 仓库。

- 目录为空(只有 `.git`)→ 全新公司,正常,继续。
- 已有内容 → 先读 `company/onboarding-state.md`:有未完成的 onboarding 就播报进度并续走;没有该文件但库里有别的内容,停下来问清楚是不是要在现有库上补建,避免覆盖。
- 读写失败或不是 git 仓库 → 停止,按「失败排查」告诉管理员怎么修。

### 1. 访谈(行业适配器,语音友好)

按顺序问,每问一轮就复述确认。问题开放,不预设行业:

1. **公司是做什么的?**(一两句话;追问:客户是谁、卖什么/做什么服务)
2. **日常最常被问的 3-5 类问题是什么?**(这直接决定数据目录怎么分——贸易行是订单/客户/报价,律所是案件/合同/判例,车队是赛程/规章/器材)
3. **有哪些高频术语/黑话?**(建术语表)
4. **手头有哪些资料?**(PDF/表格/照片/聊天记录——先登记类型,入库用 anc-ingest)
5. **团队有谁,各管什么?**(姓名/角色/关注面)
6. **哪些事实经常变?**(名单、价格表、排期——这些要进 canonical 单点文件)

然后建**问题模型**(勘探的本质不是收集信息,是建立问题模型)。五问,答不出就写 `TBC`,全部标「假设」:

7. **核心瓶颈**:制约你们业务目标的关键环节是哪一个?(追问:如果三个月后什么都没变,最先出问题的是哪里)
8. **因果链**:它是技术原因、流程原因、外部约束还是内部能力不足?(逐条列)
9. **量化影响**:它让你们损失了什么?时间、收入、满意度?现在能拿到哪个数字?(区分实测 / 系统记录 / 估算)
10. **相关方地图**:谁被它影响?谁有动力推动解决?谁会阻碍?
11. **已有尝试**:之前试过什么?为什么没成?

问完复述一遍「我理解你们最堵的是 X,因为 Y,每周大约损失 Z」,让管理员纠正;这句话就是第一批 skill 的立项依据。

### 2. 设计目录(给用户看,确认后再写)

根据回答设计 3-6 个业务目录(用问题 2 的答案命名,如 `orders/` `clients/` `cases/`),外加固定骨架:

```
CLAUDE.md            # 根路由:问题类型 → 目录/文件 对照表 + 使用纪律(公司 bot 回答前先读它)
CONTRIBUTING.md      # 入库规范(见步骤 3)
company/profile.md   # 公司简介(访谈产物)
company/glossary.md  # 术语表
company/team.md      # 成员与角色(canonical:人员信息只在这一份)
company/problem-model.md  # 问题模型(canonical:五要素 + 状态 + 证据,诊断层)
collab/              # 协作规范 + 任务看板 + 决策记录 + 交接模板(多人多 agent 共用一个库)
roles/<role>.md      # 每角色一份:职责、常见问题、口吻建议
<domain>/CLAUDE.md   # 每业务目录一份:本目录放什么、怎么命名
<domain>/_originals/ # 原件区(PDF 等,结构化 markdown 用 source_file 指回)
templates/           # 数据录入模板(复制→填→写入)
skills/<name>/SKILL.md  # 技能正文(见步骤 3)
```

### 3. 逐个写入(直接写文件,每类文件写完提交一次)

提交信息格式:`onboarding: <写了什么>(<管理员姓名>)`。

- **根 CLAUDE.md** 必须包含:① 公司一句话简介;② 「问题类型 → 文件」路由表(按问题 2 生成);③ 三条纪律:先按表定位再搜索、查不到就说「尚未入库」不编造、易变事实只在 canonical 文件维护。
- **CONTRIBUTING.md**:frontmatter 规范(`title` / `source_file` / `updated`)、目录与命名约定、「原件进 `_originals/`,结构化 markdown 指回原件」。
- **问题模型与协作模板**:把本技能目录下 `vault-templates/company/problem-model.md` 按访谈第 7-11 问填好(答不出的要素写 `TBC`,状态一律「假设」,第 6 节列出立项候选)写入 `company/problem-model.md`;`vault-templates/collab/` 四个文件原样写入 `collab/`(公司若已有自己的协作规范,先读后并,不覆盖)。
- **技能正文**:把本技能目录下 `vault-skills/` 里的每个 `<name>.md`,按需结合访谈结果做行业定制(尤其入库规范相关表述),写入 vault 的 `skills/<name>/SKILL.md`。正文第一个标题下方必须保留两行——`触发词:…` 与 `简介:…`,各自单行、非空、≤200 字;写入前逐个自检,缺了就补。从此技能正文以 vault 为唯一真相:改技能 = 管理员改 vault。
- 找不到本技能目录(WorkBuddy 安装 skill 的位置不确定时)→ 请管理员给出路径,或从仓库 `workbuddy/skills/anc-onboard/` 复制到主机后告诉你路径。
- 其余文件按访谈内容填,没问到的字段写 `TBC`。

### 4. 收尾清单(打印给管理员)

1. 回到 `HOST-SETUP.md` 第 8 步,**收紧控制文件权限**。在这之前,不要把公司 bot 绑定到企业微信。
2. 告诉成员:在企业微信里找公司 bot 问公司的事;把资料发给它并说「入库」,它会走 anc-ingest。
3. 问题模型里的每个「假设」都需要证据:下一步是逐人访谈,把访谈纪要入库并在 `company/problem-model.md` 回填证据链接;每个里程碑复盘先看哪些假设变成了「已验证 / 已推翻」。

## 失败排查

- 写入报「拒绝访问」→ 控制文件权限已收紧(第 8 步之后属正常),或公司 bot 的 Windows 用户对 `C:\anc` 没有修改权限,回 `HOST-SETUP.md` 第 3 步。
- `git status` 报「不是 git 仓库」→ 回 `HOST-SETUP.md` 第 3 步执行 `git init`。
- `git` 报 `dubious ownership` → 仓库不是由当前用户创建的,按 `HOST-SETUP.md` 第 3 步的说明设置 `safe.directory`。
- 找不到 `git` 命令 → 主机没装 Git for Windows,或装完后没重新登录。
